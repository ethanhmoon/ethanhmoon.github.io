gym tracker

A lifting log built on one rule: the past is immutable. Every set you log is appended, never edited, so a personal record from March is still there in September. Every statistic — estimated one-rep max, best volume, longest streak — is derived from that history on read rather than stored and mutated. Ships inside hunter.

the problem

Most workout apps store your current numbers and quietly overwrite them. Edit a set, correct a typo, resync a device, and last spring's best lift is gone — along with any ability to answer "am I actually stronger than I was in March?" The data model treats progress as a value, when it's really a history.

So I built it the other way round. Logged sets are facts about a date and are never modified. Personal records aren't fields you update; they're the answer to a query over immutable rows. That single choice makes the whole feature set fall out for free — streaks, trend charts, and four kinds of PR are all just different aggregations.

how it works

Nothing below the sets table is a source of truth. Delete every derived number and it rebuilds identically from the log.

what I built

  • Append-only workout history — logging is an insert, so nothing ever overwrites a past personal record immutable log
  • Six fixed muscle-group categories rather than free-text labels, which keeps every row aggregatable and prevents the taxonomy drifting into "chest", "Chest", and "chest day" 6 categories
  • Estimated one-rep max via the Epley formula, so a heavy triple and a lighter set of ten become comparable numbers on the same axis epley 1RM
  • Four independent record types tracked automatically — heaviest weight, best single-session volume, best individual set, and longest active streak 4 PR types
  • Weight and volume charts that update the instant a set is logged, rendered client-side from local rows with no request in the loop chart.js
  • Shares hunter's SQLite file and FastAPI host, so it's one process and one backup rather than a second app to maintain no extra infra

decisions worth defending

01

Append-only, and derive everything else

The sets table is the only source of truth. PRs, streaks, and trends are queries, not stored state — so they can never disagree with the history that produced them, and a bug in the stats layer is a bug in a function, not corruption in a table.

trade-off: correcting a mistyped set means logging a compensating entry, and reads get more expensive as history grows. Both are cheap at personal-log scale.

02

A closed category set, not free text

Free-text labels feel flexible and destroy your ability to group anything six months later. Six fixed categories mean every historical row remains comparable to every new one without a cleanup migration.

trade-off: exercises that don't fit get filed approximately. Consistent aggregation beats precise-but-unusable taxonomy.

03

A published formula over a bespoke model

Epley is one line, well documented, and independently checkable — anyone can verify the number the app shows them. Fitting my own estimator on my own limited data would have been less accurate and impossible to audit.

trade-off: Epley drifts at very high rep counts. Known, bounded, and documented in the UI rather than hidden.

04

Offline is a feature, not a fallback

Gyms have bad signal, and a tracker that spins while you're resting between sets doesn't get used. Every read and write hits local storage, so charts redraw immediately and there's no loading state to design around.

trade-off: no cross-device sync. Consistent with hunter's local-first posture — one file, yours, backed up how you like.

what I'd build next

Materialised stats with invalidation. Deriving on read is correct but linear in history length. A cached aggregate keyed on the latest row id would keep correctness and flatten the cost.

Per-exercise 1RM curves. The data already supports it — it's a grouping change, not a schema change, which is the payoff of modelling this as an event log.

Export. An append-only log is the easiest thing in the world to hand back to its owner as CSV. If the pitch is that the data is yours, leaving should be trivial.
