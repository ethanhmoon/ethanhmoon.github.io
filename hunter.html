hunter

A job aggregator I built because I was the user. It pulls full-time new-grad postings from 13 ATS boards and aggregators, collapses the duplicates, scores every listing with rules I can read, and quietly hides the ones that have already closed. Runs entirely on your machine — no account, no server, no telemetry.

the problem

Applying to new-grad roles is a data quality problem wearing a career costume. The same posting appears on four aggregators under three titles. Half the listings on any given board are already filled but still indexed. Every job site wants an account before it will show you anything, and then ranks by whoever paid for placement.

I wanted one list I could trust: deduplicated, ranked by criteria I chose, and honest about which postings are dead. The interesting engineering isn't the scraping — it's identity, freshness, and making 13 fragile upstream sources behave like one reliable table.

how it works

Ingest and serving are separate concerns joined by one SQLite file. The liveness loop treats stored postings as a cache of a remote truth and re-checks them rather than trusting them.

what I built

  • An adapter per upstream board, each responsible for one API or markup quirk and all emitting the same normalised posting record 13 sources
  • Canonical-URL identity: strip tracking parameters and fragments, then key on the result — the same role syndicated across four aggregators collapses to one row url dedupe
  • A deterministic scorer — same input, same score, every run. No model, no randomness, and every point in a listing's score is traceable to a rule explainable
  • Liveness pass on every refresh that re-requests stored postings and auto-hides anything returning 404 or 410, so closed roles stop wasting your time 404/410 check
  • Test suite covering adapters, normalisation, dedupe, and scoring — the safety net that makes changing a fragile adapter a five-minute job instead of a gamble 344+ tests
  • Ships as a local FastAPI app against a single SQLite file: clone, run, open localhost. No signup, no hosting bill, no data leaving the machine local-first
  • Sustained iteration rather than a weekend push — sources added, adapters repaired, scoring tuned against real applications 125+ commits

decisions worth defending

01

Deterministic scoring, not a model

An ML ranker would have been the flashier choice. But I had no labelled data, no way to evaluate it, and a hard requirement that I be able to answer "why is this job ranked third?" Rules give me reproducibility and unit tests; a model would have given me a plausible-looking black box.

trade-off: the rules need hand-tuning as my priorities change. That's a config edit, and it's visible — which is the point.

02

Local-first, SQLite, no accounts

The moment there's a hosted backend there's auth, a database bill, a privacy policy, and a migration story. SQLite plus localhost removes all four. Your search history stays on your disk, and the whole app is one file you can back up or delete.

trade-off: no sync across devices, and single-writer concurrency. Correct call for a tool with exactly one user.

03

Verify freshness, don't assume it

Most aggregators show you postings they indexed weeks ago and never revisited. I treat the local table as a cache with no TTL guarantee from upstream, so every refresh re-requests stored listings and demotes the dead ones on the evidence of an actual HTTP status.

trade-off: more outbound requests per refresh. Bounded by checking only what's already stored, and hiding rather than deleting so a flaky 404 is recoverable.

04

Tests as the contract for fragile inputs

13 upstream sources means something breaks most weeks — a renamed field, a changed layout, an added redirect. The 344+ tests exist because scraped input is adversarial by nature. When a board changes, a test tells me which adapter and which field, in seconds.

trade-off: fixtures need refreshing as real responses drift. Cheaper than debugging silent data corruption downstream.

what I'd build next

Title-similarity dedupe. URL identity is cheap and correct but conservative. Near-duplicate detection on normalised titles plus company would catch the rest.

Adapter health monitoring. If a source silently returns zero results for three runs, that's a broken adapter, not an empty board. It should page me.

Application tracking. The natural next table: what I applied to, when, and what came back — closing the loop between the scoring rules and the outcomes that would validate them.
