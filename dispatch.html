dispatch

the problem

Every mainstream news app optimises for time-on-app. The feed is deliberately bottomless, the ranking is opaque, and the topics you care about get diluted by whatever is trending. If you follow three subjects closely, you end up scrolling past forty stories to find them.

Dispatch inverts that. Topic selection is the product, not a settings-menu afterthought. You declare your topics up front, the backend only stores and serves stories that match, and the feed has a bottom you can actually reach. Getting there meant treating "what counts as this topic" as a data modelling problem rather than a ranking problem.

how it works

Ingest runs independently of serving. The client never talks to a news source directly — it only ever reads rows that have already been normalised and tagged.

what I built

  • Ingest layer that pulls from multiple publishers and flattens every response into one internal story shape, so adding a source is a config change rather than a code change source adapters
  • Postgres schema in Supabase with stories, topics, and a join table — the many-to-many is explicit, so one story can legitimately belong to two topics without duplicating the row 3 core tables
  • Express API exposing a small, boring surface: fetch the feed for a user's topics, list available topics, read and update preferences REST
  • URL-keyed upserts so re-running ingest is idempotent — the same story syndicated across three outlets doesn't become three feed items idempotent
  • Mobile-first client built and tested against iOS Safari first, then widened out, rather than shrinking a desktop layout down iOS first
  • Continuous deploys from main to Vercel with Supabase credentials held as environment secrets, never in the bundle live

decisions worth defending

01

Normalise on the way in, not on the way out

Each publisher returns a different shape. I convert to a single internal story record at ingest time, so the API and client only ever handle one format and per-source weirdness is quarantined in one adapter.

trade-off: a schema change means backfilling stored rows. Worth it — the alternative is source-specific branching leaking into every read path.

02

Managed Postgres over a hand-rolled backend

Supabase gave me real Postgres — joins, constraints, indexes — plus auth I didn't have to write. For a solo project the thing that kills momentum is rebuilding session handling, not writing queries.

trade-off: platform coupling. Mitigated by keeping business logic in Express and treating Supabase as a database, not a framework.

03

Idempotent ingest, keyed on canonical URL

Ingest is an upsert, not an insert. Re-running it is safe, a failed run can simply be retried, and syndicated duplicates collapse into a single row before they ever reach a feed.

trade-off: URL is an imperfect identity — tracking params and AMP variants slip through. Canonicalising before hashing catches most of it.

04

Explicit topics instead of a recommender

A model that infers interest would be more impressive to build and worse to use — cold start, feedback loops, no way to tell it it's wrong. Declared topics are inspectable and instantly correctable.

trade-off: no serendipity. A "related topics" surface is the honest way to add discovery without giving up user control.

what I'd build next

Scheduled ingest. Move the fetch loop onto a cron trigger with per-source failure isolation, so one publisher going down doesn't stall the run.

Read state. Persisting what you've already seen is what turns a filtered feed into a genuinely finite one.

Stricter deduplication. Title-similarity matching on top of URL canonicalisation, to catch the same wire story republished under four different headlines.
