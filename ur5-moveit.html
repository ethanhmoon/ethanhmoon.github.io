ur5 motion stack

A ROS 2 Humble workspace that takes a target point in space and turns it into a collision-free trajectory a UR5 arm actually executes — planning through MoveIt2, simulating in Gazebo, and containerised so the whole toolchain comes up the same way on any machine. Built during my work at Argonne National Laboratory.

the problem

"Move the gripper to this point" is one sentence and about six hard problems: solve inverse kinematics for a 6-DOF arm, find a path through free space that avoids the arm hitting itself or the table, turn that path into a time-parameterised trajectory the controllers can follow, and do it repeatably enough that you'd trust it near real hardware.

Sampling-based planners make the last part the interesting one. They're stochastic — the same goal can produce a different path every run, and occasionally no path at all within the time budget. A demo that works once isn't a motion stack. Most of my effort went into making end-to-end execution boringly repeatable.

how it works

The command node never computes joint angles. It states where the end-effector should be; MoveIt2 owns kinematics, collision checking, and planning.

what I built

  • End-to-end simulation and motion planning pipeline for a UR5 manipulator — goal in, executed trajectory out moveit2 · gazebo
  • A Python node that drives the arm to precise Cartesian targets through pymoveit2, keeping the command interface in task space rather than joint space pymoveit2
  • Tuned RRT* planning parameters — planning time budget, goal tolerance, and solve attempts — for reliable end-to-end trajectory execution instead of occasional success RRT*
  • Generated and hand-corrected the MoveIt2 configuration package for the arm: planning groups, joint limits, and the collision matrix ur5_moveit_config
  • Fully containerised ROS 2 Humble workspace, so the toolchain, dependencies, and simulator versions are pinned and reproducible on any host docker
  • Supporting packages covering ROS 2 fundamentals — custom interfaces, services, and clients — built as the working foundation for the control node 6 packages

decisions worth defending

01

Command in task space, not joint space

The node asks for an XYZ pose and lets MoveIt2 solve IK. Publishing joint angles directly would have been simpler and would have thrown away collision checking, joint limit enforcement, and any ability to retarget to a different arm.

trade-off: less direct control over the exact configuration reached. The right answer when the goal is a position, not a pose.

02

Tune for repeatability, not planning speed

RRT* is asymptotically optimal but stochastic — short time budgets give you fast paths that sometimes fail or come out ugly. I traded planning latency for a success rate I could rely on across repeated runs, because an intermittent failure in a motion stack is worse than a slow one.

trade-off: higher latency per goal. Acceptable for point-to-point positioning; would need revisiting for reactive motion.

03

Containerise the whole toolchain

ROS 2 plus Gazebo plus MoveIt2 is a dependency graph that breaks differently on every machine. Pinning it in a Docker image means "it works on mine" stops being a caveat — the environment is an artifact, versioned alongside the code.

trade-off: GUI forwarding and device passthrough add friction. Paid once, in the Dockerfile, instead of on every fresh setup.

04

Simulate first, and mean it

Gazebo isn't a stand-in for hardware here, it's the test harness. A planning bug that would cost a self-collision on a real UR5 costs a restarted process in simulation, so I could be aggressive about probing failure modes.

trade-off: sim-to-real gap in dynamics and contact. Fine while the questions are about planning and kinematics.

what I'd build next

Planner benchmarking. Run the same goal set across RRT*, RRTConnect, and BiTRRT and record success rate, planning time, and path length. Turn the tuning I did by feel into numbers.

Perception-driven goals. The 2022 work here used sensor-driven control through inverse kinematics; wiring a camera into the planning scene closes the loop between seeing an object and reaching for it.

Hardware bring-up. The same MoveIt2 config should drive a physical UR5 through the UR driver. That's where the sim-to-real assumptions get tested for real.
